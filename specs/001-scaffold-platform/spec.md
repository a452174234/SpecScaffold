# 功能规格说明：SpecScaffold Web 脚手架平台

**功能分支**: `001-scaffold-platform`
**创建日期**: 2026-04-30
**状态**: 草稿
**输入**: 用户描述："基于 Harness Engineering 的 Web 端图形化使用脚手架项目，使用 Spec Kit 或 Open Spec 作为 SDD 能力的提供方，使用 Claude Code 或 Codex 作为大模型调用能力，强制在工程执行前完成基于 TDD 的测试用例完善后再执行业务开发"

## 用户场景与测试

### 用户故事 1 - 创建脚手架项目（优先级：P1）

用户（开发者）打开 SpecScaffold Web 界面，通过图形化引导创建一个新的工程项目。系统引导用户选择工程模板、配置项目参数（项目名称、目标平台等），并在完成后在本地生成对应的项目结构。

**优先级理由**: 这是平台的核心入口，没有项目创建能力，其他所有功能都无法使用。

**独立测试**: 可通过创建一个完整的项目并验证生成的项目结构来独立测试。

**验收场景**:

1. **给定** 用户打开系统首页，**当** 用户点击"新建项目"并填写项目名称和选择模板后，**则** 系统生成完整的项目目录结构并显示创建成功
2. **给定** 用户正在创建项目，**当** 用户未填写必填字段时，**则** 系统提示缺少的必填项，不允许继续

---

### 用户故事 2 - 导入现有项目（优先级：P1）

用户在 Web 界面中输入本地已有项目的目录路径，系统扫描该目录并识别项目结构（语言、框架、目录布局），将项目导入系统。导入后用户可以直接在该项目上启动 SDD + TDD 迭代开发流程。

**优先级理由**: 支持现有项目迭代是核心需求，与新建项目同等重要。

**独立测试**: 可通过导入一个已有项目并验证系统正确识别项目结构来独立测试。

**验收场景**:

1. **给定** 用户在首页点击"导入项目"，**当** 用户输入有效的本地目录路径后，**则** 系统扫描目录结构，识别项目类型并展示项目概要信息
2. **给定** 用户输入了无效或不存在的目录路径，**当** 系统尝试验证路径时，**则** 提示路径无效，要求用户重新输入
3. **给定** 项目已成功导入，**当** 用户打开项目后，**则** 可以直接进入 SDD 流程开始迭代开发

---

### 用户故事 3 - SDD 规格驱动开发流程（优先级：P1）

用户在项目中启动 SDD 流程，系统通过集成的 Spec Kit 或 Open Spec 引擎，引导用户从自然语言描述生成规格说明（Spec），再从 Spec 生成实施计划（Plan）和任务列表（Tasks）。整个流程通过 Web 界面图形化呈现。

**优先级理由**: 规格驱动开发是平台的核心方法论，与项目创建同等重要。

**独立测试**: 可通过创建一个 Spec 并验证其生成 Plan 和 Tasks 的完整链路来独立测试。

**验收场景**:

1. **给定** 用户已创建项目，**当** 用户输入功能描述并点击"生成规格"后，**则** 系统通过 SDD 引擎生成包含用户场景、需求和成功标准的完整规格文档
2. **给定** 用户已生成规格文档，**当** 用户点击"生成计划"后，**则** 系统生成包含技术上下文、项目结构和实施阶段的计划文档
3. **给定** 用户已生成计划，**当** 用户点击"生成任务"后，**则** 系统生成按优先级排序、带依赖关系的任务列表

---

### 用户故事 4 - AI 大模型集成与代码生成（优先级：P2）

用户在任务执行阶段，系统通过集成的 Claude Code 或 Codex 大模型能力，辅助用户完成测试用例编写和业务代码实现。用户可以在 Web 界面中查看 AI 的执行过程和结果。

**优先级理由**: AI 能力是平台的核心差异化特性，但依赖 SDD 流程生成的任务作为输入。

**独立测试**: 可通过选择一个任务并验证 AI 辅助生成测试用例和代码的完整过程来独立测试。

**验收场景**:

1. **给定** 用户选择了待开发的任务，**当** 用户点击"AI 生成测试用例"后，**则** 系统调用大模型生成对应任务的测试用例代码，并在界面中展示
2. **给定** 测试用例已生成并确认，**当** 用户点击"AI 实现代码"后，**则** 系统调用大模型生成实现代码，并自动运行测试验证
3. **给定** AI 生成的代码未通过测试，**当** 测试失败时，**则** 系统展示失败信息并允许用户重新生成或手动修改

---

### 用户故事 5 - 强制 TDD 工作流管控（优先级：P2）

系统强制执行 TDD 工作流：每个任务必须先完成测试用例编写（Red 阶段），测试用例通过审批后才能进入业务代码开发（Green 阶段）。系统在流程管控上阻止跳过测试直接编写业务代码的操作。

**优先级理由**: TDD 强制执行是项目的核心原则，确保代码质量，但需要 SDD 流程和 AI 集成的基础能力先行。

**独立测试**: 可通过尝试在不同阶段执行操作并验证系统的流程管控行为来独立测试。

**验收场景**:

1. **给定** 任务处于"待开发"状态，**当** 用户尝试直接编写业务代码时，**则** 系统拒绝操作并提示"请先完成测试用例编写"
2. **给定** 测试用例已编写完成，**当** 用户提交测试用例审批并通过后，**则** 系统将任务状态变更为"可开发"并解锁业务代码编辑
3. **给定** 业务代码已编写完成，**当** 用户运行测试全部通过后，**则** 系统自动触发 Git 提交保存变更

---

### 用户故事 6 - 安全围栏与操作审计（优先级：P1）

系统在 AI 智能体执行任何操作时强制执行安全围栏策略：项目范围外的操作仅允许只读（包括 MCP 查询网页等）；项目范围内的操作按风险级别管控。高危操作执行前 MUST 暂停并向用户展示操作说明（做什么、为什么、影响范围），经用户审批后方可执行。所有操作 MUST 记录审计日志。

**优先级理由**: 安全围栏是 Harness Engineering 的核心——"人类掌舵"的前提是人类能审查和控制智能体的行为。

**独立测试**: 可通过让 AI 尝试执行不同级别的操作并验证系统的拦截/放行/审计行为来独立测试。

**验收场景**:

1. **给定** AI 智能体尝试执行项目范围外的写操作，**当** 操作被拦截时，**则** 系统拒绝操作并记录审计日志
2. **给定** AI 智能体尝试执行项目范围外的只读操作（如 MCP 查询网页），**当** 操作通过安全检查时，**则** 系统允许执行并记录日志
3. **给定** AI 智能体尝试执行项目范围内的高危操作（如删除文件、执行 Shell 命令），**当** 操作触发审计时，**则** 系统暂停执行，向用户展示操作说明（操作内容、目的、影响范围），等待用户审批
4. **给定** 用户收到高危操作审计请求，**当** 用户点击"批准"后，**则** 系统执行该操作并记录审批结果
5. **给定** 用户收到高危操作审计请求，**当** 用户点击"拒绝"后，**则** 系统取消该操作并通知 AI 智能体

---

### 用户故事 7 - 工具组件管理（优先级：P3，v2 实现）

用户可以在系统设置中管理外部工具组件的配置：切换 SDD 引擎（Spec Kit ↔ Open Spec）、切换 AI 模型（Claude Code ↔ Codex）、查看各工具的能力边界文档。切换操作无需修改业务代码。

> **注**: 此故事延后到 v2 实现。v1 仅通过抽象接口预留扩展能力（FR-007），不提供工具管理界面（FR-009）。

**优先级理由**: 工具可替换性是架构层面的保障，但对核心功能流程不构成阻塞。

**独立测试**: 可通过切换 SDD 引擎并验证同一功能描述仍能正常生成 Spec 来独立测试。

**验收场景**:

1. **给定** 用户在工具管理页面，**当** 用户将 SDD 引擎从 Spec Kit 切换为 Open Spec 后，**则** 后续的规格生成功能仍可正常使用
2. **给定** 用户在工具管理页面，**当** 用户点击某个工具的"能力文档"后，**则** 系统展示该工具的能力边界文档（能做什么、不能做什么、已知限制）
3. **给定** 用户在工具管理页面，**当** 用户将 AI 模型从 Claude Code 切换为 Codex 后，**则** 后续的代码生成功能使用新的模型执行

---

### 边缘场景

- 当 SDD 引擎服务不可用时，系统如何处理正在进行的规格生成？
- 当 AI 模型调用超时或返回异常时，用户的任务状态如何回滚？
- 当用户在 TDD 流程中强制刷新页面或断开连接时，如何恢复当前进度？
- 当多个用户同时操作同一项目时，如何处理冲突？
- 当 AI 智能体连续触发多个高危操作时，审计流程如何避免阻塞开发节奏？
- 当用户长时间未响应审计请求时，AI 智能体应该如何处理？（已由 FR-021 回答：无限暂停等待）

## 需求

### 功能需求

- **FR-001**: 系统 MUST 提供基于 Web 的图形化界面，支持项目创建、项目导入、SDD 流程引导、AI 辅助开发的全流程操作
- **FR-002**: 系统 MUST 集成至少一种 SDD 引擎（Spec Kit 或 Open Spec），支持从自然语言描述生成规格说明
- **FR-003**: 系统 MUST 支持从规格说明自动生成实施计划和任务列表
- **FR-004**: 系统 MUST 集成至少一种 AI 大模型能力（Claude Code 或 Codex），支持测试用例生成和业务代码生成
- **FR-005**: 系统 MUST 强制执行 TDD 工作流：测试用例编写 → 审批通过 → 业务代码开发，不允许跳过
- **FR-006**: 系统 MUST 在每个功能通过测试验证后自动触发 Git 提交
- **FR-007**: 系统 MUST 将所有外部工具（SDD 引擎、AI 模型）通过抽象接口集成，支持运行时切换
- **FR-008**: 系统 MUST 为每个接入的外部工具维护能力边界文档
- **FR-009**: 系统 MUST 提供工具管理界面，展示已接入工具的状态和能力文档
- **FR-010**: 系统 MUST 在 AI 生成代码后自动运行对应的测试用例并展示结果
- **FR-011**: 系统 MUST 保存用户的操作进度，支持断点恢复
- **FR-012**: 所有用户界面文案和文档内容 MUST 使用中文
- **FR-013**: 系统 MUST 支持通过指定本地目录路径导入已有项目，扫描并识别项目结构
- **FR-014**: 系统 MUST 为已导入的项目提供与新建项目相同的 SDD + TDD 迭代开发能力
- **FR-015**: 系统 MUST 实现安全围栏策略：操作边界由项目 Spec 文档定义的功能范围与平台通用安全边界共同界定；项目范围外的操作仅允许只读，项目范围内的操作按风险级别管控
- **FR-016**: 系统 MUST 对高危操作（如文件删除、Shell 命令执行、系统级修改）执行前暂停，向用户展示操作说明并等待审批
- **FR-017**: 操作说明 MUST 包含：操作内容、执行目的、预期影响范围
- **FR-018**: 系统 MUST 记录所有操作的审计日志至平台本地数据库，包含操作类型、执行者、时间、审批结果
- **FR-019**: 系统 MUST 阻止 AI 智能体执行未经审批的高危操作
- **FR-020**: 用户审批结果（批准/拒绝/附带反馈）MUST 作为上下文注入回 AI 智能体，智能体据此调整后续行为
- **FR-021**: 审计请求等待期间，AI 智能体 MUST 暂停执行，不设超时，直到用户明确响应

### 关键实体

- **项目（Project）**: 用户创建的工程项目，包含项目配置、生成的文件结构、关联的 Spec/Plan/Tasks
- **规格说明（Spec）**: 由 SDD 引擎从用户描述生成的规格文档，包含用户场景、功能需求、成功标准
- **任务（Task）**: 从 Plan 拆分出的具体开发任务，包含状态（待测试/测试中/可开发/开发中/已完成）、关联的测试用例和代码
- **工具适配器（ToolAdapter）**: 外部工具的抽象接口实例，记录工具类型、配置、状态、能力边界文档
- **工作流状态（WorkflowState）**: 项目在 SDD + TDD 流程中的当前状态，用于管控流程推进
- **安全策略（SecurityPolicy）**: 定义操作分级规则的安全策略，包含平台通用安全边界（所有项目共享）和项目级 Spec 边界（每个项目独立），操作级别判定（只读/低危/高危）和对应处理方式
- **审计记录（AuditLog）**: 存储在平台本地数据库中的操作审计信息，包含操作类型、目标、风险级别、审批状态、用户决策、时间戳

## 成功标准

### 可度量成果

- **SC-001**: 用户可以在 5 分钟内完成项目创建并获得初始项目结构
- **SC-002**: 从输入功能描述到生成完整的 Spec 文档，平均耗时不超过 60 秒
- **SC-003**: SDD 引擎切换后，同一功能描述的规格生成成功率不低于 90%（v2 验证）
- **SC-004**: AI 生成的测试用例中，至少 80% 可以直接运行不报语法错误
- **SC-005**: 强制 TDD 流程下，零测试的代码提交发生率为 0%
- **SC-006**: 工具切换操作（SDD 引擎或 AI 模型）在 10 秒内生效，无需重启系统（v2 验证）
- **SC-007**: 安全围栏拦截所有越权操作的命中率为 100%（项目外写操作、未审批高危操作）
- **SC-008**: 高危操作审计请求从生成到展示给用户的延迟不超过 2 秒

## 澄清记录

### 会话 2026-04-30

- Q: v1 版本的工具集成范围？ → A: v1 仅实现 Claude Code + Spec Kit，预留 Codex 和 Open Spec 的扩展接口，工具管理界面延后到 v2
- Q: 是否需要支持现有项目？ → A: 必须支持在现有项目基础上做迭代开发
- Q: 用户如何将现有项目导入系统？ → A: 通过指定本地目录路径导入，系统扫描并识别项目结构
- Q: Web 后端如何调用 Claude Code？ → A: 通过 CLI 子进程执行 `claude` 命令，捕获 stdout/stderr
- Q: Spec Kit 的调用方式？ → A: Spec Kit 以 Claude Code Skills 形式集成，通过 Claude Code CLI 间接调用。具体调用链需在 Plan 阶段分析源码确认
- Q: Web 应用的部署形态？ → A: 本地 Web 服务，用户在终端启动后通过浏览器访问 localhost
- Q: "Harmness 工程"的含义？ → A: 应为 Harness Engineering（参考 OpenAI 文章），核心理念是"人类掌舵，智能体执行"——工程师设计环境、明确意图、构建反馈回路，AI 智能体负责执行。SpecScaffold 本身就是 Harness 的具象化

### 会话 2026-04-30（安全围栏）

- Q: 安全围栏的核心需求？ → A: 强制只允许执行规范内的操作，高危操作需要用户审计并展示操作作用说明
- Q: 操作分级策略？ → A: 按影响范围分级。项目外仅允许只读操作（含 MCP 查询网页等）；项目内按风险级别管控
- Q: 审批结果如何反馈给 AI？ → A: 审批结果作为上下文注入回 AI 智能体，智能体根据结果决定下一步（继续/调整/终止）
- Q: 用户未响应审计请求时如何处理？ → A: AI 智能体暂停等待，直到用户响应，不设超时
- Q: "规范内的操作"中"规范"指什么？ → A: 项目 Spec 文档定义的功能范围 + 脚手架平台的通用安全边界，两者共同界定
- Q: 审计日志存储在哪里？ → A: 存储在平台本地数据库（如 SQLite），与项目文件分离

## 假设

- 用户具备基本的软件开发知识，理解项目脚手架和 TDD 的概念
- v1 版本仅集成 Spec Kit（SDD 引擎）和 Claude Code（AI 模型），通过抽象接口预留扩展能力
- Spec Kit 以 Claude Code Skills 形式集成，通过 Claude Code CLI 间接调用（调用链需在 Plan 阶段分析源码确认）
- Claude Code 通过 CLI 子进程方式调用（执行 `claude` 命令），系统捕获其 stdout/stderr 获取输出
- 用户的开发环境已安装 Git，系统可以自动执行 Git 操作
- 项目初始版本为单用户模式，暂不考虑多人协作冲突
- 系统必须支持导入已有项目进行迭代开发，不仅限于从零创建新项目
- Web 应用以本地服务形态运行，用户在终端启动后通过浏览器访问 localhost
- 项目基于 Harness Engineering 理念构建，核心理念是"人类掌舵，智能体执行"：
  工程师设计环境（Spec）、明确意图（SDD）、构建反馈回路（TDD），AI 智能体负责执行
- SpecScaffold 本身即是 Harness 的具象化——为 AI 编程提供结构化的工作环境
